# Immutable prepared-artifact contract — increment 13

This is an isolated, pure candidate contract and persistence design, **not** an
installed DocType or a durable ledger. No runtime generator/worker/HTTP adapter
uses it yet. No customer invoice, identity, counter, PIH, credential, file or
database schema was changed; no tenant inspection or remote request was made.

## Implemented declarations and invariants

`issuance_candidate.py` has no Frappe, filesystem, clock, signing or HTTP access.
The only inputs are immutable typed declarations and bounded exact XML bytes.
Unknown/ambiguous input fails with static internal codes, not raw caller values.
There is no new UI/whitelisted method. A future adapter must translate these codes
before presenting messages; existing English/Arabic UI behavior is unchanged.

| Object | Purpose and limit |
| --- | --- |
| `IssuanceScope` | Saved-source identity, API environment, explicit chain mapping reference, legacy unit reference and positive issuance version; not verification of the saved source or chain |
| `DeclaredCredentialEpoch` | Company/device owner declaration, canonical UUID version reference and public certificate/key fingerprints; no keys, auth or verified ownership |
| `PreparationContext` | Freeze the scope, epoch, validated route and source snapshot digest declarations; not an atomic live credential or accounting snapshot |
| `PreparedIssuanceCandidate` | Preserve exact immutable XML bytes; derive metadata, observed certificate and versioned manifest/key fingerprints; no persistence, acceptance or dispatch authorization |

All nested objects are frozen and validated at construction. Mutable dictionaries
are not accepted as contexts. XML strings/bytearrays are not accepted as issued
bytes. Derived fields are `init=False` and recomputed on construction, including
`dataclasses.replace`; they cannot be independently injected as caller claims.

The source names use an internal 140-character bound and valid UTF-8, without
normalization, trimming or filename construction. Slash and Unicode invoice names
remain identities. Stable chain and epoch IDs must be explicit canonical nonnil
UUID references, not raw credential text or the legacy auth-derived fingerprint.
Supplying those references does **not** establish a verified mapping or epoch.

## Scope key versus content manifest

The versioned structured key contains schema version, Production document purpose,
Company, invoice DocType/name, API environment, stable chain ID and issuance
version. Canonical JSON avoids delimiter-concatenation collisions. Sales and POS
with equal names, different environments/chains and explicit versions stay distinct.
Environment is not inferred from the legacy Production-purpose counter column.

The key deliberately excludes XML, snapshot digest, certificate/epoch, current
unit reference and API URL. Changing one of these must remain detectable drift
under the same invoice/version key, not silently manufacture a replacement key.
The content manifest additionally binds those declarations, exact-file SHA-256,
derived UUID/ICV, declared invoice digest/PIH, type/indicator and observed public
certificate/key/text fingerprints. The XML itself retains QR and all other fields.

`compare_prepared_candidates` checks the structured scope as well as its key
hash, then reports exact-byte, taxpayer, unit reference, epoch, route and snapshot
drift. An empty tuple means only that these declared candidates agree; it is not
permission to insert, replay, select an authoritative artifact or claim acceptance.
Changing the version number does not grant a correction/reissue right either.

Manifest JSON canonicalization is internal bookkeeping, not invoice XML C14N or
ZATCA invoice/SignedProperties/certificate hashing. XML is never reserialized,
reformatted, resigned or regenerated by this contract. The declared XML invoice
digest and PIH are retained but are not cryptographically verified.

## Type and route binding

The canonical root InvoiceTypeCode must be unique/scalar, with code 388/381/383/386
and a seven-position indicator beginning with 01 or 02 and binary remaining flags.
The candidate binds 01 to the application's clearance operation and 02 to its
reporting operation, rather than trusting current B2C settings over the XML.
Its route is revalidated through the existing pure resolver, even if a caller
constructs an ApiRoute manually. Unknown operations, wrong environment/purpose,
unsafe URL configuration, onboarding, Debug and Compliance are excluded.

These type values and the 386 advance-invoice identity are documented in the
[ZATCA XML standard v1.2, section 11.2.1](https://zatca.gov.sa/ar/E-Invoicing/SystemsDevelopers/Documents/20230519_ZATCA_Electronic_Invoice_XML_Implementation_Standard_%20vF.pdf).
This small structural check is not full flag/business-rule, XSD, advance-allocation,
tax/accounting, signature, QR or SDK validation. Advance calculations and ERP
accounting remain separately gated. The standard also distinguishes transformed
invoice/PIH hashing (BR-KSA-26) from a whole-file fingerprint; this contract does
not replace that algorithm with its manifest hash.

The current candidate format requires the application's prepared signed-XML
structure and embedded certificate matching declared public fingerprints. This
is an application-format restriction, not a claim that every standard invoice
must contain a producer signature. Unsigned standard formats, returned clearance
artifacts and Phase-1 outputs need separate contracts; do not re-sign or overwrite
an original candidate with a returned artifact.

## Privacy and proof limits

Exact XML and raw API URL are excluded from repr and diagnostic projection.
Use `diagnostic_projection`, never generic dataclass serialization in logs/UI.
Immutable Python bytes are not encrypted storage, permission enforcement or a
durability guarantee. No keys/auth are accepted or resolved by this model.

Diagnostics leave persistence, epoch, chain mapping, source snapshot, counter
continuity, XSD, invoice hash, QR, signature, remote acceptance and replay
verification false. Self-signed certificate and invalid XML-signature fixtures
intentionally show that structural consistency does not establish trusted issuance.

## Proposed persistence boundary — not implemented

1. Build a verified, versioned ERP source snapshot and effective settings; map
   historical issuing units/counters to explicit stable chain IDs on restored data.
2. Under the actual chain-owner lock/transaction, select a protected verified
   credential epoch, allocate/retain identity once and freeze the prepared bytes.
   Bind the private signing and public HTTP credential material atomically without
   storing raw auth in a manifest or changing an existing chain on rotation.
3. Store an access-controlled immutable artifact plus manifest in a unique scoped
   issuance record. Recompute/compare bytes, key and structured scope on read;
   equal keys with different manifests fail reconciliation. Record creation time
   and provenance separately. Commit before dispatch through a durable outbox.
4. Append request attempts/outcomes separately, with one active dispatch lease.
   Unknown transport, auth failure, validation rejection and confirmed acceptance
   are different events. Never derive acceptance from saved display status alone.
5. Retain clearance/response artifacts as distinct related evidence. Update live
   status/PIH idempotently only from the confirmed endpoint-response contract.
6. Replay original stored bytes only after authorization, epoch/chain verification,
   accounting reconciliation and state/lease checks. Corrected rejected versions
   require an explicit tested policy, not automatic UUID/ICV regeneration.

No DocType JSON, hook, repository, dispatch policy, correction rule, queue, lease,
SQL uniqueness/lock or migration is installed by this increment. Those are real
remaining work, not guarantees supplied by the frozen in-memory objects.

## Verification

237 new local tests cover the eight type/class combinations across Sales/POS and
three environments, advance identity, exact-byte preservation, immutability,
constructor revalidation, bounded/static failures, UTF-8/structured keys, route
revalidation, declared certificate/key matching and same-key drift in XML,
UUID/ICV/PIH, epoch renewal/owner, source snapshot and unit/endpoint references.
Tests poison database/filesystem/HTTP entry points to prove this core does no I/O.
The combined selected suite passes 1,887 cases in v15/Python 3.10 locally.

No actual site/SQL/Frappe transaction, ERPNext 16, browser, ZATCA SDK or HTTP
acceptance result is claimed. Next implement/test the append-only outcome and
dispatch-state contract, then persistence/credential/chain provenance and isolated
restore rehearsal before wiring any runtime adapter or deploying to a pilot.
